# dps-store-garment

가먼트 프린터 출력 클라이언트 (Windows, Electron)

주문 관리에서 넘어온 출력 큐를 받아 디자인과 작업지시서를 출력한다.
`equip-sync-g-module`(Python) 을 대체하며, **자동 업데이트**를 지원한다.

## 개발

```bash
pnpm install
pnpm dev        # 빌드 후 실행
pnpm lint       # 타입 검사
pnpm build:win  # 설치본 생성 (release/)
```

## 배포

태그를 밀면 GitHub Actions 가 빌드해 릴리즈를 발행한다.

```bash
git tag v0.1.1 && git push origin v0.1.1
```

- 릴리즈는 **draft 가 아니라 published** 로 나가야 한다. draft 는 자동 업데이트가 보지 못한다
  (`electron-builder.yml` 의 `releaseType: release`)
- 과거 릴리즈는 최신 2개만 유지한다

## 자동 업데이트

확인 시점은 **앱 시작 시**와 **설정의 수동 버튼** 둘뿐이다. 주기 확인은 하지 않는다.
출력 도중 재시작을 부추기지 않기 위해서다. 받아둔 업데이트가 있어도 자동으로 재시작하지 않고,
적용 시점은 작업자가 고른다.

## 설정 저장 위치

파이썬 판은 실행 폴더의 `config.ini` 를 썼지만, 여기서는 **사용자 데이터 폴더**의
`config.json` 에 둔다. 설치 폴더는 쓰기가 막혀 있을 수 있고 자동 업데이트로 통째로
교체되므로, 그대로 두면 업데이트마다 API 키와 프린터 설정이 날아간다.

## 작업지시서

파이썬 판은 reportlab 좌표로 PDF 를 그린 뒤 프린터에 보냈다. 그 레이아웃 주석이 줄마다
"웹 다운로드와 동일"을 가리키는 데서 보이듯, **원본은 웹의 HTML 이고 PDF 는 그것을 좌표로
옮겨 적은 사본이었다.** 옮겨 적는 과정에서 폰트 임베딩 문제로 인쇄물 글자가 통째로 비던
사고도 났다.

여기서는 사본을 만들지 않는다. 웹과 같은 HTML 을 그려 숨은 창에서 그대로 인쇄한다.
PDF 생성도, 폰트 임베딩도, PDF 를 프린터에 밀어 넣는 단계도 없다.

> **실물 대조가 끝나야 3단계가 끝난다.** 화면에서 맞아 보여도 드라이버가 여백·배율을
> 다르게 잡을 수 있다. 대기 목록의 「미리보기」 버튼이 지시서를 PDF 로 떨구니, 현행
> 프로그램 출력물과 A4 흑백으로 견준다.

## 벤더 자산

레포는 공개다. 그래서 **벤더 원본 파일명을 git 에 남기지 않는다.**

```
vendor/cli_legacy.bin  →  .vendor-build/cli_legacy.exe   (중립 이름)
vendor/cli_legacy.lib  →  .vendor-build/<원본 라이브러리 이름>
vendor/.dll_manifest   ← git 미추적. CI 는 secret VENDOR_DLL_MANIFEST 로 주입
```

복원 결과는 `asarUnpack` 으로 설치본에 들어간다. 실행 파일은 `child_process` 로 불러야
해서 asar 밖에 있어야 하지만, 이름이 중립이라 곧바로 눈에 띄지는 않는다.
암호화가 아니라 노출을 줄이는 것이며, 파이썬 판이 PyInstaller 로 exe 안에 넣던 것과
목적이 같다.

매니페스트가 없으면 실행 파일만 복원되고 **장비 전송이 빠진 빌드**가 나온다. 빌드를
막지는 않는다 — 개발 중에는 벤더 자산 없이도 나머지를 확인할 수 있어야 한다.

## 장비 여러 대

한 단말에 장비를 여러 대 물릴 수 있다. 같은 장비에 두 건을 동시에 밀면 벤더 CLI 와 장비가
엉키므로 **장비마다 실행 줄을 하나씩** 두어 차례로 보내고, 장비끼리는 동시에 나간다.
파이썬 판이 프린터당 워커 스레드를 하나씩 띄우던 것과 같은 구조다.

분배는 `round_robin`(번갈아)과 `single`(첫 대만) 두 가지다. 상태 조회와 관리 명령은
**대표 장비 한 대**에만 보낸다 — 전 대에 돌리면 조회가 겹치고 어느 대의 답인지도 갈리지 않는다.

전송 방식은 `cli` 가 기본이고, `direct` 는 변환한 이미지를 프린터로 그대로 인쇄한다.
벤더 자산이 없거나 CLI 가 듣지 않을 때의 물러설 자리이며, 잉크·플레이트 설정을 실을 수 없어
장비 패널 설정을 따른다.

## 감시 폴더

서버 큐와 별개로, 다른 시스템이 폴더에 떨궈 놓은 파일(PDF·PNG·JPG)도 출력한다.
파이썬 판 `watcher.py` 와 같은 자리다. 기본은 꺼짐이다.

복사가 끝나기 전에 집으면 잘린 파일이 나가므로 **크기가 멈출 때까지 기다린 뒤** 담는다.
집은 파일은 폴더 안 `done/`, 담지 못한 파일은 `error/` 로 옮긴다. 서버 큐에 없는 건이라
다운로드·완료·실패 보고는 올리지 않는다.

## 장비 관리와 상태

설정 화면에서 흰색 잉크 순환, 자동 클리닝, 인쇄 버튼 잠금·해제, 메뉴 잠금·해제,
장비 로그 수집을 보낼 수 있다. 모두 **LAN 으로 연결된 장비 전용**이고, 출력 중에는 막는다.

장비 상태 조회도 LAN 전용이고 기본은 꺼짐이다. 조회 자체가 장비 호출이라 전송과 겹치면
장비가 바쁠 수 있다. 오류는 정상에서 오류로 넘어가는 순간에만 알린다 — 오류가 이어지는
동안 매 주기 알리면 로그가 오류로만 채워진다.

## 진단

전송이 깨지면 `logs/diagnostics/` 에 보고서가 쌓인다. 현장에서 깨지는 원인은 대개
코드가 아니라 PC 상태라, 실행 정보와 함께 다음을 담는다.

- 벤더 자산의 Windows 차단 표식(NTFS `Zone.Identifier`)과 PE 아키텍처
- VC++ 재배포 런타임 존재 여부
- 인쇄 스풀러 상태, 프린터 드라이버와 큐 목록

「보낸 인쇄 데이터를 진단 폴더에 남긴다」를 켜면 장비로 보낸 데이터를 되풀어 원본·XML·
이미지로 남긴다. 무엇을 보냈는지 확인하는 유일한 경로지만 건마다 파일 세 개가 쌓이므로
기본은 꺼짐이다.

## 로그

화면 로그와 별개로 `logs/app.log` 에 남는다. 5MB 를 넘으면 직전 것 하나만 남기고
새로 시작한다. 설정의 「로그 폴더」 버튼으로 연다.
